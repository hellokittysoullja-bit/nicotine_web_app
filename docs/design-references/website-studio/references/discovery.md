# Discovery and Project Routing

Use discovery to produce a decision-ready brief, not a long interview. Inspect what already exists before asking the user to repeat it.

## Establish the Project Surface

For an existing project, identify its framework, package manager, routes, data sources, design system, deployment configuration, and current user-visible behavior. Preserve working conventions unless the requested outcome requires a change.

For a new project, establish:

- intended audience and the primary job they need to complete;
- business or communication outcome;
- primary action the site should encourage;
- required content, brand material, and media;
- route count and content ownership;
- forms, search, persistence, uploads, authentication, payments, or integrations;
- local-only, private-preview, internal, or public delivery;
- accessibility, localization, compliance, and deadline constraints.

Do not infer permission to publish, purchase services, create accounts, or expose private material.

## Ask Only Useful Questions

Ask one to three short questions at a time. Skip anything already answered in the request, workspace, or supplied assets. Useful questions usually resolve one of these uncertainties:

1. Who is the site for, and what should they do next?
2. What content or proof must be visible?
3. What should the experience feel like?
4. Which capabilities or user states are required?
5. Where and to whom will it be published?

If the user grants creative freedom, choose a direction and state the assumptions. Do not turn preference gathering into a blocker.

## Choose an Execution Path

Use the **fast path** when all of the following are true:

- one route or a very small static route set satisfies the request;
- content is known or can be drafted safely;
- no durable records, uploads, authentication, payments, or external operational data are required;
- the existing project does not require architectural changes.

Use the **capability path** for existing-site changes with meaningful complexity, multi-route products, durable data, search indexes, uploads, authentication, external systems, complex forms, or role-specific behavior.

Both paths require responsive implementation, accessibility, build validation, and visual review. The fast path reduces planning and architecture work; it does not reduce quality.

## Route to an Archetype

Choose one primary recipe based on the visitor's main job. Add at most one secondary recipe when it clarifies a real second job.

- Landing page: understand an offer and take one action.
- Portfolio: assess work and decide whether to engage.
- Editorial story: understand a subject through a guided narrative.
- Knowledge hub: find and use accurate information.
- Directory or catalog: discover, filter, and compare entries.
- Dashboard: understand current state and investigate change.
- Portal: complete role-specific tasks.
- Tracker or workflow: create records and move work through states.

Do not combine recipes merely to make the site appear more substantial.

## Produce the Brief

Record:

- user job and primary action;
- primary and optional secondary archetype;
- required routes and sections;
- content and data owners;
- required interactions and complete state list;
- art-direction sentence and unresolved design decisions;
- technical capabilities and integrations;
- responsive and accessibility obligations;
- delivery target and access model;
- assumptions, exclusions, and acceptance criteria.

## Discovery Exit Check

- [ ] The primary audience, job, and action are explicit.
- [ ] The fast or capability path is justified.
- [ ] One primary archetype has been selected.
- [ ] Required content, data, media, and permissions are understood.
- [ ] Every requested capability has an owner and a state model.
- [ ] Publication scope and access expectations are explicit.
- [ ] Unknowns that could materially change the result are resolved or clearly recorded.
